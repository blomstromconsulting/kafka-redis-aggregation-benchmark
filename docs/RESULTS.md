- A1 Streams: aggregators 1.37 cores / 3,455 MiB; Kafka broker 0.41 cores / 3,524 MiB.
- A2 Classic: aggregators 1.15 cores / 3,467 MiB; Kafka broker 0.39 cores / 3,915 MiB.

Kafka Streams pays for state durability with changelog writes and one standby replica per task (extra broker load and RocksDB memory in the aggregator pods); B pays with a separate Redis server.

## Recommendation

Basis: result-ready latency (to the moment the result exists, without the persistence step); the end-to-end figures are in the tables above.

No variant met the 500 ms p99.95 SLO in every executed target-load scenario (A1 Streams: FAIL, A2 Classic: FAIL, B Redis: FAIL), so none can be recommended as is for the stated requirement.

The pod-disruption scenarios (S2–S5) do not have one consistent leader; compare the scenario rows above to see where each variant fails, and note INCONCLUSIVE runs that were limited by the laptop rather than the design.

Between the two Kafka Streams variants (identical code, different rebalance protocol): A2 Classic was clearly ahead in 2 and A1 Streams in 0 of 4 pod-disruption scenarios (same rule: non-overlapping ranges, ≥ 10%).

## Limitations of this environment

- Single OrbStack node: all pods share one VM, one disk and one kernel; node failures, cross-node networking, rack awareness and independent failure domains are not reproduced.
- The local profile has one Kafka broker and one Redis node; broker failover and Redis replication are only exercised in the HA profile (`./scripts/deploy.sh --ha`).
- Other workloads on the same cluster share CPU and memory; runs whose node CPU p95 exceeded 90% are marked INCONCLUSIVE.
- All timestamps come from the same node clock; cross-machine clock skew is not present here but would be in production.
- All variants write their actions to one shared PostgreSQL instance on the same VM, so stalls of that write path appear in every variant's end-to-end latency (result-ready and aggregation-only latency exclude it). Result ready omits the publishing step that replaces persistence in production; in A it already includes the transactional Kafka hop to the executor, in B no Kafka publish at all.
- Steady and failure windows are assigned by the broker append time of an action's source fragment; an action appended shortly before a fault and delayed by it counts as steady. Whole-window figures (used for S2–S5 above) do not depend on this rule; its effect per run is quantified by `scripts/analysis/window_sensitivity.py` (see `docs/ANALYSIS-NOTES.md`).
